# Runtime image security

## October 14 hardening decision

The final application, database and maintenance images keep the tested Node 24.21.0 and PostgreSQL 16.14 versions and their pinned Bookworm base digests. The official tags still resolved to the existing digests when checked on October 14, 2026. Re-pulling the same tags therefore does not supply the available Debian security updates. Switching to Trixie could remove additional Bookworm findings, but changes the operating-system and native-library compatibility boundary. This patch instead installs explicitly selected Bookworm security revisions through APT, which verifies Debian repository signatures and package integrity.

| Final target                       | Package                              | Security revision |
| ---------------------------------- | ------------------------------------ | ----------------- |
| Application, database and operator | perl-base                            | 5.36.0-7+deb12u4  |
| Database and operator              | perl, perl-modules-5.36, libperl5.36 | 5.36.0-7+deb12u4  |
| Database and operator              | libssl3, openssl                     | 3.0.22-1~deb12u1  |
| Database and operator              | libpcre2-8-0                         | 10.42-1+deb12u2   |

The package revisions were independently checked against the actual Debian Bookworm security ARM64 package index and the [Perl](https://security-tracker.debian.org/tracker/CVE-2026-8376), [OpenSSL](https://security-tracker.debian.org/tracker/CVE-2026-75803), and [PCRE2](https://security-tracker.debian.org/tracker/CVE-2026-103111) advisory records. A successful build is required to establish their actual installation; source declarations alone do not do so. The runtime verifiers check the installed revisions.

Global npm, npx, and Yarn are removed from the application image, while the build toolchain keeps the supported npm version. Administration now calls the compiled CLI directly. The original application scan's npm matches were in `/usr/local/lib/node_modules/npm`, separately from the clear `/app/node_modules` inventory. No package-manager dependency is needed to run the service or CLI. The deployed database and restore database use the patched `database` target, retaining the official PostgreSQL server, entrypoint and gosu behavior, service identity, and data paths. The operator derives from that same patched target and removes unused gosu, PostgreSQL's startup entrypoint, and the PostgreSQL server package, while preserving PostgreSQL 16.14 client binaries and their complete installed dependency closure. Actual export, coherent backup, and independent restore must pass before accepting that removal.

## Image and advisory evidence

A scan must bind the final image ID, export archive checksum, scanner version, vulnerability-database timestamp/checksum, raw component inventory, and unfiltered findings. Count package/advisory matches separately from unique CVEs; duplicate binary packages from one source package do not represent independent exploits. Scan the final filesystem rather than counting packages removed in later layers. Keep npm application dependencies, npm's own tooling, Debian packages, standalone binaries, and bundled native libraries distinguishable.

The pre-hardening images produced 256 application matches and 537 operator matches with Grype 0.120.1 and the October 13 database. These are historical baseline counts, not the hardened images' result. Some flagged packages are unused tooling, and some advisories require a particular function, architecture, or input path. For example, [CVE-2026-5450](https://security-tracker.debian.org/tracker/CVE-2026-5450) requires a particular malloc-backed scanf conversion and Debian classifies its Bookworm status as a minor issue. Such qualifications require evidence; they are not grounds for suppressing all OS findings. Remediation and remaining findings are reviewed against the actual hardened-image scan.

## Bundled native image libraries

Syft's ordinary package inventory identifies the sharp/libvips npm package, but does not enumerate all of libvips's linked component versions. The compiled `nativeImageInventory()` export in `apps/server/dist/native-image-inventory.js` captures `sharp.versions`, the process-wide JPEG-buffer/PNG-buffer loader policy, and narrowly scoped advisory assessments with primary references. Capture this inside both exact images in addition to their package-manager SBOMs. The allowlist is installed at the shared image-decoder module boundary; both upload validators use it. Task-image bytes are decoded from the same no-follow file descriptor used for checksum and magic-byte validation. Task-image validation allocates one buffer sized to the recorded file length, bounded by the 50 MiB upload limit. Every chunk is checked against the remaining capacity, and the final byte count must match before decoding. Non-image attachments remain streamed. It does not change output encoders and is not a claim that all native code is vulnerability-free.

The HEIF component's affected versions remain installed, but its decoder is excluded from the application's input execution path. The PNG assessment is specifically tied to the reviewed libvips 8.18.7 source path; it must be reviewed again when that linked version changes. Future callers must retain the shared boundary rather than importing an unrestricted decoder directly. Version-based supplemental CPE queries are useful leads, but broad or unknown constraints require checking the upstream advisory and compiled execution path before concluding that an installed component is affected.

Run each exact image's embedded native-notice validator as well, and record its emitted count rather than assuming a fixed bundle size. The earlier integrated images validated 1,140 file hashes and 390 source references. Comparing them with the original working-directory images identified exactly three upstream build helpers absent from clean checkouts: `build-provenance/build/posix.sh`, `build-provenance/build/wasm.sh`, and `build-provenance/build/win.sh`. All 1,140 common hashes and all 390 source references matched.

The three helpers are now tracked through an exact-path exception to the broad `build/` ignore rule. Each file is byte-identical to both the previously reviewed local helper and the pinned upstream commit `ebb95f8add54eee8bed840e3fb587e4cbec857d7`. A clean index checkout must contain their executable files and resolve the top-level upstream `build.sh` references. Rebuild and validate the application and operator images after this packaging correction; the emitted notice count belongs to that new artifact, not the earlier images. Restoring these helpers resolves the known checkout omission without establishing original-binary reproduction.

The [original native-source provenance gate](native-image-licenses.md#remaining-release-gate), including the unpublished post-update Cargo lock and original compiler/image identities, remains separate for external redistribution. Local packaging checks do not establish source delivery to recipients, complete original-binary reproduction, permanent deployment, or Apple distribution acceptance.
