# Attention and optional notifications

Today is derived from the owner's actual tasks, step dependencies, agent attempts and approval requirements, active workout, and food entries in the owner's configured time zone. Planned work remains dormant. Paused tasks, agent work and dependency blockers remain visible with their waiting reasons. Ordinary agent success creates no OS alert. A ready human step following completed agent dependencies, an approval requirement, a failed attempt, an unknown/expired outcome, or due human work can create attention.

In-app attention does not require OS permission, an Expo account, or a configured provider. `GET /api/attention` returns source IDs, revisions and opaque `{kind,id}` record routes. Durable `attention_events` retain the underlying event when delivery fails or the owner opts out. Due event identities use task ID and due instant, so unrelated edits and polling do not cause repeated alerts. Handoffs use step execution revision; result review uses result version. One event/device pair has one delivery record.

## Owner controls and registration

Notifications default off, with independent due, handoff and failure choices. Preferences are revision checked and operation-ID idempotent; changes record the human actor in the audit log. Device registration requires a current signed-in owner session and the current enabled preference revision. A token or device owned by another user cannot be registered. Disabling notifications retires registrations; enabling again requires fresh registration. Deleting/revoking/expiring the session makes its device ineligible immediately in the delivery query, and reconciliation retires it. The client also deactivates its registration before logout and cancels its owned local schedules. SecureStore scopes the stable device identity and schedule IDs to the installation.

Local due reminders and the session timer remain native notifications. Reconciliation recovers stored/orphan schedule IDs, replaces changed deadlines, cancels obsolete reminders on refresh/startup, and cancels on opt-out/logout. Permission denial leaves the underlying records and timer intact. Permission is requested only through explicit owner enablement. A notification response uses an opaque UUID route; the signed-in owner API must confirm that the record still exists before navigation. Arbitrary URLs are rejected.

## Optional Expo deployment

Keep the provider absent for a private self-hosted installation that does not need remote alerts. If enabled by the deployment's explicit `EXPO_PUSH_ENABLED=true`, configure the server's optional `EXPO_PUSH_ACCESS_TOKEN` for Expo enhanced push security; never expose that token in mobile configuration or payloads. Supply the deployment's own EAS project ID to `getExpoPushTokenAsync` through app configuration. Do not use another person's project/account ID.

Create an Expo project and configure the native bundle identifier and Apple push credentials for this deployment. Use a development or distribution build with the expo-notifications plugin, APNs entitlement and configured credentials; Expo Go is not proof of remote delivery. The operator must own the Apple Developer account/credentials and allow notification permission on the test device. Follow [Expo push setup](https://docs.expo.dev/push-notifications/push-notifications-setup/) and [Apple credentials](https://docs.expo.dev/app-signing/app-credentials/). This repository does not create accounts, buy memberships, or populate personal credentials.

The adapter follows the current [Expo send/receipt protocol](https://docs.expo.dev/push-notifications/sending-notifications/): send batches contain at most 100 messages; tickets contain a receipt ID; receipts are checked after 15 minutes. HTTP 429, network failure and 5xx are retried with bounded exponential backoff. Credential/auth failures terminate delivery with an errored state while retaining the attention event. Invalid tickets/receipts are recorded as failures. `DeviceNotRegistered` retires the registration and removes the reusable token. Pending events made obsolete or ineligible are suppressed. Receipt retrieval is bounded to 100 IDs, within Expo's limit.

A ticket marked `ok` means Expo accepted the message, so the state is `accepted`. A receipt marked `ok` means APNs/FCM accepted it, so the state is `provider-accepted`. Neither state proves the owner saw a notification. Default previews contain only a generic app alert and opaque record route; task names, food details and workout details are never included.

## Verification boundaries

`apps/server/test/attention.test.ts` uses an isolated real PostgreSQL database (`mems_life_attention_test`) for event identity, preference opt-in/disable, current-session registration/revocation, payload privacy and invalid token receipts. Provider fixtures verify HTTP batching, ticket/receipt parsing and error policy. Domain and mobile tests verify dependency waiting, opaque route validation and local scheduling/cancellation behavior. These tests do not prove APNs device delivery.

Real remote delivery is an external release gate: configure the operator's EAS project and Apple credentials, install the signed native build, explicitly grant permission, register the current device, trigger a fictional handoff/due alert, inspect ticket then receipt, observe it on the device, and open the correct authorized record. Repeat with permission denial, logout and disabled preferences. Until that gate is run, remote/native OS delivery remains unverified.
