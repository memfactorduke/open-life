# Portable access and deployment

Checked 2026-10-12. Research decision; no implementation or deployment has been validated.

## Decision

Use one TypeScript/Fastify application on Node.js 24 LTS, PostgreSQL, and embedded Better Auth. Serve the React management interface and API under one origin. Package the application and database for single-host Compose deployment behind Caddy. Keep Expo mobile and the MCP adapter as clients of the same application operations, consistent with ADR-0001 and ADR-0002. Node currently lists 24 as LTS and 26 as Current; use the supported LTS line and pin patched dependencies during implementation. [Node releases](https://nodejs.org/en/about/previous-releases), [Better Auth Fastify integration](https://better-auth.com/docs/integrations/fastify), [PostgreSQL adapter](https://better-auth.com/docs/adapters/postgresql)

| Credible option | Evidence and tradeoff | Decision |
| --- | --- | --- |
| Embedded Better Auth | MIT-licensed library with PostgreSQL, Fastify, Expo, sessions and API-key integrations. Avoids a separate identity service. Application still owns authorization. | Choose for this private installation. |
| Supabase Auth and supporting stack | Supports app-facing MCP authentication and self-hosting, but adds a broader operational stack; self-hosting leaves backups, updates and availability to the operator. | Credible later packaging alternative; unnecessary for the initial service boundary. |
| Keycloak | Separate identity server with OIDC and native-app authorization-code support. Useful when centralized identity or several relying applications justify it. | Additional identity deployment is not justified for one owner and this application. |

Sources: [Better Auth license](https://github.com/better-auth/better-auth/blob/main/LICENSE.md), [Expo integration](https://better-auth.com/docs/integrations/expo), [Supabase app-facing MCP](https://supabase.com/docs/guides/ai-tools/byo-mcp), [Supabase self-hosting responsibilities](https://supabase.com/docs/guides/self-hosting), [Keycloak OIDC](https://www.keycloak.org/securing-apps/oidc-layers), [Keycloak container deployment](https://www.keycloak.org/server/containers).

## Owner access, bootstrap and recovery

- Start with one owner account per installation. Provide a **local administrator bootstrap command**, accessible only to someone controlling the installation, that reads the owner's chosen identity and password without echoing or logging the password. The transaction refuses when an owner already exists. Public signup remains disabled; there is no unauthenticated first-visitor-wins setup page. This command is required application work, not a claim that Better Auth ships this exact workflow.
- Use Better Auth email/password authentication; the email is an owner-supplied login identifier. SMTP and email verification are not prerequisites for a locally provisioned owner. Password hashing is delegated to the library. Its documented configuration supports disabling signup. [Email/password configuration](https://better-auth.com/docs/authentication/email-password)
- Supply a local administrator recovery command that replaces the owner's password through the library's supported server-side APIs and revokes existing human sessions. Recovery must not expose a public bypass or depend on email delivery. Offer an explicit option to revoke all agent grants as well, with an audit record. Specify and test the chosen library API during implementation; never update password hashes by undocumented table writes.
- Browser: secure HttpOnly session cookie, same-origin requests, strict trusted-origin checks, and CSRF protection on application mutations as well as auth endpoints. Mobile: official Expo integration and SecureStore for session material; attach the session cookie to ordinary API requests as its documentation requires. Do not store credentials in the offline content database. [Cookies](https://better-auth.com/docs/concepts/cookies), [security protections](https://better-auth.com/docs/reference/security), [Expo integration](https://better-auth.com/docs/integrations/expo)
- Keep sessions in PostgreSQL and disable server-side cookie-session caching initially, so revocation is checked on the next authenticated request. Offline content may remain locally readable; server authorization is checked again before queued writes are accepted. Better Auth documents that cached cookies can delay revocation until cache expiry. [Session management](https://better-auth.com/docs/concepts/session-management)

## Agent access is separate

The initial required mode is **authenticated Streamable HTTP with a manually configured agent key**, tested with a generic MCP client that can send the configured authorization header. The owner creates a named, expiring, revocable grant; the raw secret is shown once. Use Better Auth's API-key plugin with hashing retained and session conversion disabled, then map the verified key to an agent principal and explicit application permissions. Restrict grant creation/revocation to the owner session. Never let a key authorize owner account recovery or credential administration. [API-key features](https://better-auth.com/docs/plugins/api-key), [hashing and session-conversion options](https://better-auth.com/docs/plugins/api-key/reference)

Configure the MCP adapter to read `Authorization: Bearer <agent-key>` and verify it through that path, without treating it as a human session. Each operation also checks its required permission and record ownership. A read-only grant cannot claim or change work. Revocation and scope changes must take effect on the next request. Grant identifiers, never secrets, belong in audit records.

**This is not OAuth interoperability.** A manually configured key is not an OAuth access token, and clients requiring automatic OAuth discovery/consent are not promised to connect. The current MCP HTTP authorization specification describes OAuth 2.1, resource metadata, resource-bound tokens and client identification; it says HTTP implementations should conform when supporting that standardized authorization mechanism. Our initial key mode is an explicit compatibility limitation, not a claim of full MCP OAuth conformance. Keep an OAuth adapter possible, but implementing discovery, consent, registration and token lifecycle is optional follow-up until a selected client requires it. Never advertise fake OAuth metadata for key mode. Generic MCP operations and the manual-header test client remain required. [MCP authorization, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)

## Portable environments

Local development uses the same schema and service, a local PostgreSQL container, fictional fixtures, and loopback endpoints. The eventual repository supplies a documented bootstrap/recovery entrypoint and example configuration containing placeholders. A physical phone needs a reachable development endpoint; `localhost` on the phone is not the development Mac.

Self-hosting uses a single Linux host with a Compose-compatible runtime, app/database persistent storage, and a reverse proxy. No hosted Supabase, Redis, external identity server, cloud agent, EAS account or paid container registry is required for this server. Caddy terminates HTTPS; the database remains private. Compose supports the same application definition across development and production, with production overrides. [Compose production](https://docs.docker.com/compose/how-tos/production/), [Fastify reverse-proxy guidance](https://fastify.dev/docs/latest/Guides/Recommendations/)

Public remote access needs reachable DNS and a certificate-valid HTTPS endpoint. Private/local access can use an operator-managed trusted certificate; Caddy's local CA is not automatically trusted by other devices. Hostname, public access method and hosting provider are operator choices, not source changes or spec blockers. [Caddy HTTPS](https://caddyserver.com/docs/automatic-https)

Supply database/auth secrets through operator-owned protected files or Compose secrets, not committed files, image layers, client bundles or logs. File-mounted Compose secrets are not an encrypted secret vault; protect the source files and backups. Retain the auth secret across restarts and include required secrets in protected recovery procedures. Back up PostgreSQL plus application attachments and verify restore into an independent installation. [Compose secret mounts](https://docs.docker.com/compose/how-tos/use-secrets/), [PostgreSQL backup](https://www.postgresql.org/docs/current/backup.html)

## Highest useful validation boundary

The buildable spec should require a clean disposable installation test spanning the real PostgreSQL database, HTTP adapters and clients: bootstrap once; reject public signup and repeat bootstrap; sign in from browser and Expo; create/read the same record through UI/API and MCP; reject absent, expired, revoked and insufficient-scope keys; revoke a human session; recover without SMTP; restart without losing records; and restore a backup into a second installation with separate configuration. Verify credentials are absent from logs and built client assets. This is stronger evidence than mocked auth tests, without requiring public hosting or a particular agent runtime.

Use a real header-capable MCP test client first. Named-client OAuth setup, external DNS/certificates, device signing/distribution, and optional SMTP are integration prerequisites only when those paths are chosen. They do not block writing or implementing this spec. Exact dependency versions, bootstrap/recovery API calls, mobile cookie forwarding and proxy settings remain implementation checks; no current evidence of an incompatibility blocks this decision.
