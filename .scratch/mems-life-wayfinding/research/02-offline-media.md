# Durable offline records, private media, and timers

Research resolved: 2026-10-12. These are first-release design choices and acceptance requirements, not implemented or tested behavior.

## Decision and alternatives

Choose a **bounded command outbox**, with Expo SQLite on iPhone/iPad and PostgreSQL as the shared authority. Persist the local record change and its queued command together; synchronize through the same authorized application operations used by web and MCP. Do not implement general table replication, CRDTs, or direct client writes to PostgreSQL.

| Option | What it buys | Remaining work and decision |
| --- | --- | --- |
| Bounded commands + change feed | Explicit product operations, one authorization/validation path, few moving services | We own retries, revisions, cursor correctness and tests. Choose this for the finite first-release record types. |
| PowerSync | Local SQLite replication, ordered upload queue and reconciliation infrastructure | Its backend still owns idempotency and conflict policy; its default last-write-wins behavior does not satisfy our no-silent-overwrite requirement. Credible later if replication scope grows. |
| Electric | Managed/general PostgreSQL read-path synchronization | Current Electric explicitly does not provide write-path synchronization; durable commands/conflicts remain application work. No first-release need for this additional read service. |

Sources: [PowerSync conflict and upload semantics](https://docs.powersync.com/handling-writes/handling-update-conflicts), [Electric write-path guide](https://electric.ax/docs/sync/guides/writes). The selection is our judgment, not a claimed limitation that these products cannot support the app.

## Mobile persistence and the synchronization contract

- Use `expo-sqlite` for downloaded server records, local drafts, pending commands, conflict copies, cursor, and timer state. A screen may say **Saved on this device** only after the SQLite transaction succeeds; distinguish **Waiting to sync**, **Synced**, and **Needs attention**. SQLite provides transactional durability; Expo documents persistence across app restarts. Use exclusive transactions for the local write/outbox boundary, rather than accidentally including unrelated asynchronous writes. [SQLite transactions](https://www.sqlite.org/transactional.html), [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/).
- Give records and commands stable client-generated IDs. Commands carry an immutable payload, operation ID, owner, target, and expected server revision. In one PostgreSQL transaction, authenticate/authorize, check revision, change records, save the operation receipt, and append change-feed entries. Replaying the same operation returns its saved result; reuse with a different payload is rejected. Retain receipt identifiers for the installation's lifetime in the first release.
- Keep confirmed server state separate from pending local changes. Apply pulled records to confirmed state, then project pending changes for display. Never discard an unsent edit because a newer server record arrived. Serialize commands within one aggregate; subsequent edits depend on the predecessor's accepted revision. A failed predecessor blocks that chain, not unrelated records. Do not silently rebase edits onto somebody else's changes.
- Retry timeouts, connection failures, and transient server errors with bounded exponential backoff/jitter; honor retry hints. A timeout means **outcome unknown**, not failure: resend the same ID. Persist attempts across restart. Validation/conflict errors stop the affected chain with a useful message; expired authentication pauses sending while local capture remains available. No infinite rapid retry loop.
- Synchronize on launch, foreground/reconnect and after local writes; use bounded polling while foregrounded. A live connection may accelerate updates but is not correctness-critical. First-release background transfer is best effort, with no promise to upload while terminated. Apple decides when background tasks run and grants limited runtime. [Apple background strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app).

### Conflicts, deletion, and cursors

- Use revision conflicts, not timestamp/last-write-wins replacement. Preserve both versions and offer **keep server**, **apply my change after review**, or **save as a new record** where meaningful. A workout session is an aggregate: concurrent editing of that session requires review; separate sessions do not conflict. Editing a plan never rewrites an already started session.
- Deletion is a revision-checked tombstone. If an edit arrived first, the stale delete conflicts; if a delete arrived first, the stale edit conflicts and cannot resurrect the old ID. Keep its local content recoverable. “Save as new” uses a new ID. Deleting a parent makes child operations reject visibly. Retain tombstones and feed history initially; do not add pruning without a full-resnapshot contract. Deletion is not an assertion that backups or already issued media links have instantly disappeared.
- Every UI, MCP and integration write uses the same feed. Assign each owner's feed position through a transactionally updated, row-locked counter, held until commit; append all affected records under that transaction position. This modest per-owner serialization is suitable for a private installation. Do **not** use creation timestamps or assume a PostgreSQL sequence is commit order: sequences can be allocated before a later/aborted commit. [PostgreSQL row locks](https://www.postgresql.org/docs/current/explicit-locking.html), [sequence semantics](https://www.postgresql.org/docs/current/functions-sequence.html).
- A page never splits one transaction position. Apply the entire page and advance its cursor in the same local transaction. A repeated page is harmless. Initial snapshots include a watermark from the same consistent database snapshot; subsequent changes start after it. A reset/invalid cursor requires a fresh snapshot while retaining the local outbox and conflict copies. Include an installation epoch so restoring the server to an older backup cannot quietly strand clients beyond the restored cursor; restore procedure rotates the epoch.

## Offline scope and platform differences

After initial sign-in and loading, mobile can view downloaded records, create/edit/finish workouts, capture food, create Planned tasks, and edit ordinary task content. Download task text, plans and recent history; fetch older history/media on demand. Show the available offline range rather than pretending uncached history exists. Keep all unsent records/media regardless of cache limits.

Require online confirmation for release into an executable queue, completion of a prerequisite that can release agent work, approval, claims/leases, run-result submission, workflow/dependency changes affecting execution, permission changes, external actions and WHOOP refresh. These are not queued as if already successful. For a timeout, show pending confirmation and reconcile the original operation. Ordinary edits to actively running work must still pass server revision/state checks.

Web is **online-first** in this release: retain visible form content after a failed request, but never label it saved before confirmation. Durable offline web editing and background upload are not promised. This avoids relying on Expo SQLite's alpha web implementation or making browser storage equivalent to the native store. Browser storage has quotas and possible eviction; even persistent-mode requests require handling failures. [Expo SQLite web status](https://docs.expo.dev/versions/latest/sdk/sqlite/), [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/).

Logout/account switching must not silently delete pending work: show the pending count and require explicit discard or allow synchronization first. Partition local stores by installation and account. Uninstalling/erasing a device can destroy unsent data; local durability is not remote backup.

## Private food photos

Choose a **private persistent filesystem volume** mounted only into the application for the initial single-host Compose deployment. PostgreSQL holds ownership, upload state, attachment references and checksums; bytes live outside the image/container writable layer and outside the web static root. Docker volumes survive container replacement, but still require backup and can be explicitly deleted. [Docker volumes](https://docs.docker.com/engine/storage/volumes/).

Compared with an S3-compatible service, this avoids another service or vendor account and fits the selected one-host deployment. Its cost is routing media bandwidth through the app, sharing the host's capacity/failure boundary, and coordinating database/file backups. S3 is a later adapter when independent capacity, direct uploads or multiple application hosts are needed, not an initial prerequisite. S3 can supply signed uploads and conditional writes, but signed URLs are bearer access until expiry and add lifecycle work rather than removing it. [S3 signed URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), [conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

1. Capture/import into an app-owned **document** directory before acknowledging the photo as saved. Picker/camera/cache URIs are not the durable record. Stage a copy, verify readable bytes/size, then commit its attachment metadata and queued work. A failed copy/storage-full leaves a visible unsaved capture, never a broken “saved” attachment. Reconcile staged/orphan files on startup; never sweep a file referenced by pending work. Expo distinguishes document storage from cache storage that the system may delete. [Expo FileSystem](https://docs.expo.dev/versions/latest/sdk/filesystem/).
2. The authenticated service allocates a stable upload ID, opaque file ID and expected checksum/size; never accept a client-supplied filesystem path or use an original filename as a storage path. Stream a bounded upload into an exclusively created staging file on the **same volume** as finalized files. Enforce request size, time and concurrency limits and fail cleanly on full disk. Validate actual size, checksum and decodable allowed image type before exposing the attachment; reject executable/non-image content regardless of filename/MIME claim. No public upload URLs or storage credentials are needed.
3. Serialize finalization by upload ID. Flush validated bytes, atomically rename the staged file into its reserved immutable final path on that volume, then commit the authorized PostgreSQL attachment/receipt transaction. Do not overwrite an existing final file: verify it matches the same upload/checksum or fail. Filesystem rename and PostgreSQL commit are **not one atomic transaction**: a crash after rename leaves an unreferenced file, which retry/startup reconciliation recognizes through upload metadata. Never commit a visible attachment before finalized bytes exist. Node provides exclusive creation, rename and explicit flush primitives; flushing durability depends on OS/device behavior. The implementation must verify same-filesystem rename and directory durability on its Linux target, not assume cross-volume moves are atomic. [Node 24 filesystem APIs](https://nodejs.org/docs/latest-v24.x/api/fs.html).
4. Persist upload progress as pending/received/finalized; full-file restart is sufficient for bounded photos, with resumable multipart upload deferred. On a lost response, query/retry the same upload ID and checksum rather than create a duplicate. Recheck owner, target revision and tombstone on finalization. Never remove the sole local copy before finalized attachment confirmation. If the food entry is deleted during upload, finalization rejects; reconciliation later removes abandoned files. Detach/delete in PostgreSQL first, then retry file removal through a cleanup queue. Cleanup must coordinate with upload finalization and never remove a referenced or active-upload file.
5. Download only through an authenticated app endpoint that looks up a visible attachment and checks owner/grant permissions on every request; no static directory mount, directory listing or guessed-file access. Send private/no-store cache headers, a validated content type and `nosniff`. Locally cached media is account-partitioned. Revocation stops new authorized requests; it cannot retract already downloaded bytes or guarantee that an in-progress response vanishes. Signed reads are optional future storage behavior, not required now, and would retain their access until expiry. This is access control, not end-to-end encryption.

### Coordinated backup and restore

Use a short maintenance window for the initial backup procedure: pause mutations, upload/finalization and cleanup, drain in-flight work, take a PostgreSQL logical dump, archive the media volume plus checksum manifest and necessary protected configuration, then resume. A database dump alone is not a media backup; independently timed copies do not guarantee matching references. PostgreSQL documents that `pg_dump` provides a consistent database snapshot, not a snapshot of external files. [PostgreSQL SQL dump](https://www.postgresql.org/docs/current/backup-dump.html), [Docker volume backup](https://docs.docker.com/engine/storage/volumes/#back-up-restore-or-migrate-data-volumes).

Restore both parts into a separate installation, verify every finalized attachment's size/checksum and ownership, reconcile pending uploads/orphans, rotate the sync epoch, and test access before declaring recovery successful. Include this downtime-based backup in the documented operator workflow; online coordinated backups and storage failover are later scope.

## Timer lifecycle

Persist timer ID/generation, session, duration, running/paused state, remaining time on pause, and absolute deadline on start/resume. Use elapsed timestamps rather than decrementing a counter every second. Recompute after foreground/restart; time zone changes do not alter an absolute deadline. A device-clock change can alter recovered elapsed time: show a detectable discrepancy and allow correction rather than inventing precision.

Schedule one local notification per running timer when permitted; cancel/replace on pause, reset, finish or edit. Reconcile scheduled notifications against persisted generations at startup to cover a crash between database and notification calls. Notifications are a reminder, not the record of elapsed time. A notification never records a completed set or workout. Apple can present a scheduled notification without running the app; Expo supports scheduling/cancellation. Delivery/sound still depends on permission and system settings. [Apple local notifications](https://developer.apple.com/documentation/UserNotifications/scheduling-a-notification-locally-from-your-app), [Expo notifications](https://docs.expo.dev/versions/latest/sdk/notifications/).

Timers belong to the device that started them for alert delivery; another device may show synchronized timer information but must not silently duplicate alerts or assume control. The phone's offline timer remains usable without cross-device coordination. Web timers update while open, without a promise of background alerts. Do not keep JavaScript or an agent alive for a timer.

## Acceptance boundary for implementation tickets

- In airplane mode record a whole workout, notes, substitutions and food photos; force-quit/relaunch and recover every acknowledged change. Simulate full disk: no false saved state.
- Drop responses after server commit, replay commands/pages, and restart during synchronization: one logical record/operation, no missing changes. Independent records continue after another conflicts.
- Edit the same session on two devices; race edit/delete and parent-delete/child-edit: preserve rejected content, expose conflict, never silently overwrite/resurrect.
- Commit feed writers out of order, paginate, mutate during snapshot, and restore an older server backup: no skipped change and correct epoch/resnapshot handling.
- Kill during photo staging/upload/rename/database commit; retry a completed upload; fill server disk; delete its entry mid-upload; request another owner's image or a path traversal: recovery without duplicate attachment or unauthorized exposure.
- Replace the app container while retaining volumes, then restore a coordinated database/media backup into another installation: finalized photos still verify and authorize correctly; missing/corrupt bytes are reported rather than silently hidden.
- Start/pause/resume/change a timer, background/terminate/relaunch, deny notifications and change device time: correct persisted state, no fabricated activity, best-effort alerts only.
- Disconnect before an agent-release/approval action and lose its response after commit: no false confirmation or duplicate release.

These tests are release gates for the chosen bounded protocol. They have not been run. Dependency reevaluation is warranted if required collaboration, sync volume or selective replication outgrows this design; it is not a prerequisite for writing the first implementation specification.
